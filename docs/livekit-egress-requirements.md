# LiveKit Egress 녹화 요구사항

## 목적

팬 브라우저의 `MediaRecorder`에 의존하는 현재 녹화를 LiveKit Egress 기반 서버 녹화로
단계적으로 전환한다. 브라우저 종료나 업로드 실패에도 녹화 결과를 안정적으로 남기고,
기기와 브라우저에 관계없이 동일한 형식의 다시보기를 제공하는 것이 목표다.

## 확정 요구사항

| 항목 | 결정 |
| --- | --- |
| 대상 통화 | LiveKit을 사용하는 1:1 팬 영상통화 |
| 녹화 방식 | Room Composite Egress |
| 출력 | 양쪽 참가자의 영상과 음성이 포함된 단일 MP4 |
| 레이아웃 | PoC에서는 LiveKit 기본 합성 레이아웃 사용 |
| 시작 조건 | `recordingEnabled=true`, 팬의 녹화 동의 확인, 양측 입장으로 통화가 `ACTIVE`가 된 뒤 시작 |
| 종료 조건 | 정상 만료, 팬·인플루언서의 종료 요청, 운영자 강제 종료 시 중지 |
| 실패 정책 | 녹화 시작·진행·저장 실패가 영상통화 자체를 중단시키지 않음 |
| 저장 위치 | PoC에서는 기존 `/srv/melly/uploads` 호스트 볼륨 공유 |
| 보관 기간 | 현재 정책과 동일하게 업로드 완료 후 7일 |
| 접근 권한 | 해당 통화에 참여한 팬 본인만 조회·재생·다운로드 가능 |
| 다운로드 | 기존 10분 유효 서명 URL과 HTTP Range 재생 방식 유지 |
| PoC 동시성 | Egress 녹화 1건만 허용 |
| 운영 동시성 | 부하 측정 후 확정 |
| 기존 녹화 | Egress 검증 완료 전까지 브라우저 녹화를 제거하지 않음 |

## 상태 및 추적 요구사항

정식 연동에서는 녹화 상태를 최소 `STARTING`, `RECORDING`, `PROCESSING`, `AVAILABLE`,
`FAILED`, `EXPIRED`로 구분한다. 통화 세션과 Egress 작업을 연결할 수 있도록
`egressId`, 시작·종료 시각, 실패 사유, 출력 경로를 추적한다.

동일 통화에 대한 중복 시작 요청과 중복 webhook은 멱등하게 처리해야 한다. 통화가
녹화 시작 직후 종료되거나 백엔드가 재시작돼도 최종 Egress 상태를 다시 조회해 복구할
수 있어야 한다.

## PoC 합격 기준

1. Egress가 기존 LiveKit 및 동일 Redis DB에 연결된다.
2. 팬과 인플루언서가 입장한 테스트 방을 MP4로 녹화할 수 있다.
3. 결과 파일에서 양쪽 영상과 양쪽 음성이 정상 재생된다.
4. Egress 종료 후 MP4가 손상 없이 마감되고 구간 이동이 가능하다.
5. 브라우저를 종료해도 서버 녹화가 계속된다.
6. 녹화 실패가 통화 연결과 종료 처리에 영향을 주지 않는다.
7. 녹화 1건 실행 시 CPU·메모리·디스크 사용량을 측정할 수 있다.

- 운영 서버 배포
- 운영 동시 녹화 한도 확정
